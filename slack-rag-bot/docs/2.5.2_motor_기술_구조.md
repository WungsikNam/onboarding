# 2.5.2 motor 기술 구조

이 문서는 Guardian Motor의 **기술 구조와 데이터 흐름**을 다룹니다. 새로운 PM이 "어떻게 동작하는가"를 이해하고, PDX 기획 시 재활용/재설계 판단 기준을 제공합니다.

## 1. iDAQ 센서 — 어떻게 이상을 감지하는가

### 1.1 iDAQ란

OnePredict 자체 개발 전류 측정 DAQ(Data Acquisition) 센서. 모터가 연결된 전력 케이블에 설치하여 3상 전류(U, V, W)를 측정한다. 진동 센서와 달리 모터 본체에 직접 부착 불필요 → 설치 비용 및 시간 대폭 절감.

### 1.2 측정 사양

| 항목 | 사양 |
| --- | --- |
| 측정 대상 | 3상 전류 (U, V, W phase) |
| 샘플링 레이트 | 10 kHz |
| 1회 측정 시간 | 10초 |
| 1회 샘플 수 | 10,000 Hz × 10초 = 100,000 샘플/채널 |
| 측정 주기 | 10분 간격 (불연속 측정. 연속 스트리밍 아님) |
| 전송 데이터 크기 | 약 170 KB/회 (바이너리 포맷) |

### 1.3 전류 신호에서 고장을 어떻게 읽는가 (MCSA 원리)

Motor Current Signature Analysis(MCSA): 모터 고장이 발생하면 전류 파형의 특정 주파수 성분에 고장 지문(Fingerprint)이 나타난다.

```
정상 전류 파형 → FFT → 전원 주파수(50/60Hz) 주변에 깨끗한 스펙트럼

고장 전류 파형 → FFT → 특정 주파수에 사이드밴드(Sideband) 출현
  - 회전자 봉 파손: f_line ± 2s·f_line (s = slip)
  - 베어링 결함: f_line ± f_bearing
  - 편심: f_line ± f_rotor
```

Slip(슬립)이란 전원 주파수 기반 동기 속도와 실제 회전 속도의 차이. Slip을 정확히 추정해야 고장 주파수 계산이 가능 → v1.11.0에서 딥러닝 기반 Slip 추정으로 교체한 핵심 이유.

## 2. 전체 데이터 흐름

```
[모터 운전 중]
    ↓
[iDAQ 센서] — 10분마다 10초간 전류(U/V/W) 측정
    ↓
[SaaS: AWS S3 / On-prem: MinIO (로컬 Object Storage)]
    ↓
[Algorithm Server (Python)]
    Phase 1. 특징 추출 (Feature Extraction)
      - FFT: 주파수 성분 분석
      - Envelope 분석: 진폭 변조 성분 추출
      - Slip 추정 (딥러닝 모델, v1.11.0~)
      - 특징값(Feature) 산출: 고정자/회전자/베어링/축 관련 수십 개
    Phase 2. 진단 (ML Inference)
      - ML 모델이 Feature → 고장 확률 → 건전성 지수(HI) 산출
      - 등급 판정: 정상(>80) / 관찰(50~80) / 주의(<50)
    ↓
[PostgreSQL]
    - diagnosis_result: 진단 결과 (HI, 등급, 시점)
    - feature_ems: 추출된 Feature 값
    - feature_diagnosis: 진단에 사용된 Feature 상세
    ↓
[motor-backend API (Flask)]
    ↓
[웹 대시보드 (React)]
```

### 2.1 배치 처리 스케줄

| 항목 | 내용 |
| --- | --- |
| 스케줄러 | APScheduler (Python) |
| 실행 주기 | 매일 자정 배치 실행 |
| 타임존 지원 | 7개 타임존 (Motiva 미국 납품 대비, v1.11.0 추가) |
| 처리 내용 | 전날 수집된 iDAQ 데이터 전체에 대해 Feature 추출 + 진단 수행 |

## 3. 진단 알고리즘 원리

### 3.1 Feature 추출 단계

| 분석 방법 | 추출 정보 | 대응 고장 |
| --- | --- | --- |
| FFT (Fast Fourier Transform) | 전원 주파수 주변 사이드밴드 크기 | 회전자 봉 파손, 편심 |
| Envelope 분석 | 전류 진폭 변조 성분 | 베어링 결함, 기계적 마모 |
| Slip 추정 (딥러닝) | 실제 회전 주파수 (동기 속도 - 실제 속도) | 모든 진단의 기준점 |
| Envelope Skewness | 엔벨로프 신호의 비대칭도 | 고정자 이상 감지 (LLDPE FP 이슈 대응으로 추가) |
| CoV (Coefficient of Variation) | 변동 계수 | 고정자 이상 보조 지표 (LLDPE FP 이슈 대응으로 추가) |

### 3.2 건전성 지수(HI) 산출

```
각 부위별 Feature 값들
    ↓
ML 모델 (부위별: 고정자 / 회전자 / 베어링 / 축)
    ↓
각 부위별 이상 확률 (0~1)
    ↓
건전성 지수(HI) 변환: HI = 100 × (1 - 이상 확률)
    ↓
종합 등급 판정 (가장 낮은 부위 HI 기준)
  - HI > 80 → 정상
  - 50 ≤ HI ≤ 80 → 관찰
  - HI < 50 → 주의
```

### 3.3 알고리즘 버저닝

LLDPE FP 과다 이슈 이후 알고리즘 버저닝 도입. 사이트별로 다른 알고리즘 버전 적용 가능. 파라미터 조정 시 해당 사이트만 영향 → 다른 사이트 안정성 유지.

## 4. 백엔드 아키텍처 (motor-backend)

### 4.1 기술 스택

| 구성요소 | 기술 | 역할 |
| --- | --- | --- |
| API 서버 | Flask (Python 3.12) | REST API 제공 |
| 데이터베이스 | PostgreSQL | 진단 결과, Feature, 설비 메타데이터 저장 |
| Object Storage | AWS S3 (SaaS) / MinIO (On-prem) | iDAQ 원시 바이너리 파일 저장 |
| 캐시 | Redis | 세션, 임시 데이터 |
| 메시지 큐 | Kafka | 데이터 파이프라인 (Cyclone 스택과 동일) |
| 스케줄러 | APScheduler | 일배치 진단 실행 |
| 알고리즘 | OnePredict 자체 개발 | 전류 기반 MCSA + ML 진단 |
| 딥러닝 | Slip 추정 DL 모델 | 정확한 회전 주파수 추정 (v1.11.0\~) |

### 4.2 주요 PostgreSQL 테이블

| 테이블 | 저장 내용 |
| --- | --- |
| diagnosis_result | 진단 결과: 모터 ID, 시점, HI, 등급, 부위별 HI |
| feature_ems | 추출된 Feature 값 시계열 |
| feature_diagnosis | 진단에 사용된 Feature 상세 (엔지니어링 화면 데이터 소스) |

### 4.3 주요 API 엔드포인트

| 엔드포인트 | 역할 |
| --- | --- |
| GET /api/devices/{id}/waveforms | iDAQ 원시 파형 데이터 조회 |
| GET /api/diagnosis/... | 진단 결과 (시점/트렌드) 조회 |
| GET /api/features/... | Feature 데이터 조회 (엔지니어링 화면) |

## 5. 배포 형태: SaaS vs On-Premises

| 항목 | SaaS | On-Premises |
| --- | --- | --- |
| 데이터 저장 | AWS S3 (클라우드) | MinIO (고객사 내부 서버) |
| DB | AWS RDS PostgreSQL | 고객사 내부 PostgreSQL |
| 이메일 알람 | 활성화 가능 | 비활성화 (서버 설정 표준화 어려움) |
| 운영 비용 | 원프레딕트 인프라 비용 부담 | 고객사 인프라 + 원프레딕트 납품·설치 비용 |
| 업데이트 | 원프레딕트 자동 배포 | 고객사 방문 또는 원격 업데이트 |
| 적용 고객 | 빙그레, 여주에너지서비스, GS파워, E1 | GS칼텍스, 한화토탈에너지스, 삼성전자 |

### 5.1 On-Premises 납품 시 필수 확인 항목

```
□ 고객사 내부 서버 사양 확인 (MinIO, PostgreSQL 설치 가능 여부)
□ 네트워크 방화벽 설정 확인 (iDAQ → 서버 포트 개방)
□ 이메일 알람 제약 사전 고지
□ SSL 인증서 관리 주체 확인 (자동 갱신 vs 수동)
□ 루텍 HW 포함 여부 확인 (LLDPE 사례: HW 없어 랙+클라이언트 PC 추가 필요)
```

## 6. Cyclone 연계 여부 분석

Guardian Motor는 가디원 터보(ClickHouse)와 달리 **Cyclone과 동일한 기술 스택**(Ceph + Iceberg + Kafka)을 일부 공유합니다. 단, 운영 결과(PostgreSQL)는 Cyclone 데이터 플랫폼과 직접 연결되어 있지 않습니다.

| 항목 | Guardian Motor | Cyclone | 연계 여부 |
| --- | --- | --- | --- |
| 원시 데이터 저장 | S3/MinIO (iDAQ 바이너리) | Ceph (Bronze 계층) | 간접 연결 가능 |
| 데이터 파이프라인 | Kafka | Kafka | 스택 공유 |
| 모델 학습 데이터 | CDC 동기화로 Production DB → Bronze/Silver | Bronze/Silver/Gold 레이크하우스 | CDC 연동 |
| 운영 결과 (진단) | PostgreSQL (diagnosis_result) | Iceberg + Ceph | 미연결 |
| 모델 레지스트리 | 자체 관리 | Cyclone이 관리 | Cyclone이 Motor DI 모델 담당 |

**핵심 포인트**:

* Motor DI(Data Intelligence) 모델 학습은 Cyclone이 관리. CDC 동기화로 Production PostgreSQL 데이터가 Bronze/Silver 계층으로 흐름.
* 운영 결과(PostgreSQL의 diagnosis_result)는 Cyclone 플랫폼과 직접 연결 안 됨. 통합 플랫폼 구성 시 별도 커넥터 또는 CDC 추가 필요.
* 가디원 터보(ClickHouse 단독)와 달리 Motor는 연계 경로가 이미 일부 존재 → 통합 OS 구성 시 Motor가 더 유리한 출발점.
