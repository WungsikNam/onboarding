## 1. 제품이 존재하는 이유

### 1.1 해결하는 문제

| **문제** | **증상** | **Cyclone의 해결** |
| --- | --- | --- |
| **데이터 탐색 병목** | 원하는 테이블 찾으려고 담당자에게 전화·이메일 → 업무 시간의 40% 낭비 | 통합 검색 + 메타데이터 자동 색인 |
| **데이터 신뢰 붕괴** | 어렵게 찾은 데이터가 결측치·노이즈 → 분석 결과 왜곡 | DQ Score + 인증 등급 마크 (Bronze/Silver/Gold) |
| **거버넌스·보안 공백** | 어떤 테이블에 개인정보·국가핵심기술이 있는지 파악 불가 → 유출 리스크 | RBAC + ABAC 태그 기반 접근 제어 |

### 1.2 한 줄 요약

> **"사내의 수많은 데이터 자산(테이블, 버킷, AI 모델 등)에 메타데이터를 자동 수집·색인하고, 도메인·태그·용어집을 붙여 누구나 구글처럼 검색하고 신뢰할 수 있게 만드는 사내 데이터 도서관 포털"**

### 1.3 제품 구분 — 반드시 구별할 것

| **구분** | **대상** | **설명** |
| --- | --- | --- |
| **Cyclone Standalone** | 고객사 납품용 | 독립 상품. 독자 UI 보유. **기획자가 담당하는 제품.** |
| **TechFlux** (구 OneSolution Cyclone) | OnePredict 내부용 | DS/DA 연구·개발 효율화 도구. 별개 제품. |

경쟁 제품: **Databricks**. 최종 목표: Data-Platform + Experimentation-Platform 결합.

## 2. 사용자 페르소나 (5대)

| **페르소나** | **역할** | **Cyclone 주 활용** |
| --- | --- | --- |
| **데이터 엔지니어** | 인프라 가동·크롤링 관리 | 소스 연결 상태 확인, 크롤링 오류 로그 점검, DAG 파이프라인 편집 |
| **데이터 스튜어드** | 거버넌스 체계 수립 | 도메인 트리 생성, 용어집 승인, 태그 규칙 관리 |
| **데이터 오너** | 현업 부서장. 데이터 자산 책임자 | 자산 설명 작성, 도메인·태그 지정, 접근 신청 승인 |
| **데이터 소비자** | 공정 분석가, BI 개발자 | 통합 검색 → 품질 배지 확인 → 샌드박스 실험 → 분석 도입 |
| **공장 관리자** | 라인·공장 책임자 | 대시보드 이상감지 알림 확인, 긴급 조치 오더 발행 |

> **Phase 2 스토리보드 페르소나와 대응**
> Data Scientist(이수현·김도훈) = 데이터 소비자 + 데이터 엔지니어 역할 겸함
> IT 전략(박진호) = 데이터 스튜어드
> IT 인프라(최현우) = 데이터 엔지니어

### 3.2 화면 흐름 다이어그램

```
[FR-AUTH] 로그인/로그아웃
        ↓
[FR-GLB] 글로벌 레이아웃 (헤더 + 접이식 사이드바)
        ↓
[FR-HOME] 홈 대시보드
  ├─ 총 자산 현황 위젯 (도넛 차트 + Sparkline)
  ├─ 태그별 자산 분포 위젯 (막대 랭킹)
  ├─ 최근 본 항목 위젯 (최근 3개월, 최대 20개)
  ├─ 즐겨찾기 위젯 (최대 100개)
  ├─ 내 자산 위젯
  └─ 데이터 서비스 카드
        ↓
[FR-EXP] 데이터 탐색 (통합 검색 + 필터 + 트리 내비게이션)
        ↓
[FR-DET] 데이터 자산 상세
  ├─ 헤더: 자산명 / Breadcrumb / FQN 복사 / 즐겨찾기
  ├─ Overview: 도메인 / Tier / 인증 마크 / 태그 / 용어
  └─ 탭 영역
       ├─ Columns/Tables/Schemas
       ├─ [FR-LIN] 계보 (Lineage) 그래프
       └─ Sample Data (별도 권한 필요)

거버넌스 관리
  ├─ [FR-DOM]  도메인 (최대 3단계 계층)
  ├─ [FR-TAG]  태그·분류 (Classification + Tag)
  ├─ [FR-GLS]  용어사전 (Glossary > Term > Sub-term)
  └─ [FR-DQ]   데이터 품질

Phase 2 추가
  ├─ [KF-1~3]  Experiment Workspace + Model Serving
  ├─ [KF-4]    Data Source Connector
  └─ [KF-5]    DAG Editor

[Admin 전용]
  ├─ 시스템 모니터링 (Prometheus)
  ├─ 사용자·역할 관리 (RBAC)
  └─ Registered Model 관리 (MLflow)
```

### 3.3 GNB 메뉴 구성

**일반 사용자 (AUTHENTICATED)**

```
홈 → 검색 → 도메인 → DAG → 용어집 → 태그 → 계보 → 커넥터 → 실험 → 데이터품질
```

**관리자 (ADMIN_AND_MANAGER)**

```
위 전체 + 관리자 설정(/admin) → 사용자 관리 → 역할 관리 → 모니터링
```

## 4. 글로벌 레이아웃 설계 원칙

신규 기능 기획 시 4가지 패턴 중 하나에 맞춰야 한다.

### 패턴 1: Global Area (기본 구조)

```
┌─────────────────────────────────────────┐
│  [토글] [로고]   [전역검색]   [계정]     │  ← Global Header
├──────────┬──────────────────────────────┤
│  Global  │         Main Content         │
│  Nav Bar │                              │
│  (GNB)   │                              │
└──────────┴──────────────────────────────┘
```

### 패턴 2: Search 레이아웃

Header 통합 검색창 → GNB 아래 필터 + 결과 리스트.
결과 카드: Information Preview / Hierarchy Utility / Personalization 3개 영역.

### 패턴 3: Detail View 레이아웃

```
icon + Name + Version
Description
[정보1][정보2]...[정보N]      ← 메타데이터 요약 행
[Tab1][Tab2][Tab3]            ← 탭 구조
Filter | Tools | Tags
━━━━━━━━━━━━━━━━━━━━━━
탭 콘텐츠
```

### 패턴 4: Code Editor 레이아웃

```
Path / Name / Status / [Execution] [Stop] [Deployment]
Library Cell | Dataset
Code Cell (Editable Space)
Log Cell
```

→ DAG 코드 탭, Online IDE(KF-2-IDE)에 적용

## 5. Phase 1 화면별 기능 상세

### 5.1 인증 (FR-AUTH)

**화면 목적**: 서비스 접근 제어 및 사용자 식별
**구현 방식**: Keycloak OIDC. `/callback`에서 OAuth 콜백 처리 후 세션 생성

| **기능** | **상세** |
| --- | --- |
| SSO 로그인 | Keycloak OIDC 기반 |
| 직접 로그인 | 아이디/비밀번호 입력. 아이디 4~50자, 비밀번호 8~20자 |
| 비밀번호 가시성 토글 | 눈 아이콘으로 마스킹 전환 |
| 로그인 버튼 활성화 규칙 | 유효성 통과 시에만 활성화 |
| 인증 실패 처리 | 비밀번호 초기화 + 스낵바 에러 메시지 |
| 로그아웃 | 세션 완전 종료 + 로그인 리다이렉트. 뒤로 가기로 재진입 차단 |
| 권한 부족 | `/unauthorized` 페이지 |

---

### 5.2 전역 레이아웃 (FR-GLB)

**화면 목적**: 전 화면 공통 내비게이션 및 헤더

| **기능** | **상세** |
| --- | --- |
| 상단 헤더 | 좌: 사이드바 토글+로고(클릭→홈). 중: 전역 검색창. 우: 사용자 프로필 (클릭→내 정보/로그아웃) |
| 사이드바 펼침/접힘 | 아이콘+텍스트 ↔ 아이콘만+툴팁 |
| RBAC 메뉴 제어 | admin/manager만 관리자 설정 메뉴 노출. URL 직접 접근 시 `/unauthorized` 리다이렉트 |

**RBAC 역할 구조**:

```
System Admin → Domain Admin → Member → Viewer
MANAGE ⊃ MODIFY ⊃ SELECT ⊃ BROWSE
```

---

### 5.3 홈 대시보드 (FR-HOME)

**화면 목적**: 데이터 자산 현황 허브
**레이아웃**: 독립 위젯 그리드. 각 위젯 개별 Loading/Result/Empty/Error 상태

| **위젯** | **기능** | **정책** |
| --- | --- | --- |
| 총 자산 현황 | 도넛 차트(비율) + Sparkline(트렌드). 기간 필터(7/14/30/90일) | KST 기준 배치 스냅샷 사용 |
| 태그별 자산 분포 | 태그 연결 개수 막대 리스트. 이름순/개수순 정렬 | 권한 없는 자산은 이름도 미노출 |
| 최근 본 항목 | 최근 3개월 내 열람 이력, 최신순 최대 20개. 전역 검색과 동기화 | 개인 맞춤 히스토리 |
| 즐겨찾기 | 별 아이콘 토글. 최대 100개. 대시보드에서 즉시 해제 | 사용자별 독립 관리 |
| 내 자산 | 내가 소유한 자산 목록 | |
| 데이터 서비스 | 등록된 데이터 서비스 카드 | |

---

### 5.4 데이터 탐색 (FR-EXP)

**화면 목적**: 전체 데이터 자산 통합 검색 & 필터링
**URL**: `/search`

| **기능** | **상세** |
| --- | --- |
| 통합 검색 | OpenSearch 기반 키워드 검색 |
| 자동완성 | 검색어 Dropdown 후보군. Enter 후 결과 갱신 (Instant Search 아님) |
| 자산 트리 내비게이션 | 좌측 Asset Tree로 계층 탐색 |
| 패싯 필터 | 데이터 유형 / 서비스 / 도메인 / 태그 / 성숙도 / 중요등급 |
| **필터 로직** | **동일 그룹 내 OR, 그룹 간 AND** |
| URL 상태 동기화 | 검색어·필터 조건을 URL에 반영 → 링크 공유 시 동일 결과 재현 |
| 결과 0건 처리 | 필터 초기화 옵션 제공 |
| 도메인 필터 트리 | 최대 3단계 계층 (L1 > L2 > L3) 탐색 |

---

### 5.5 데이터 자산 상세 (FR-DET)

**화면 목적**: 개별 데이터 자산의 메타데이터 조회 및 인라인 편집
**URL**: `/:entityType/:fqn/:tab?`

**헤더**: 브레드크럼 (`[Service] / [Database] / [Schema] / [Table]`) + 즐겨찾기 + FQN 복사

**6개 탭**:

| **탭** | **내용** |
| --- | --- |
| 개요 | 설명(편집), 도메인, 담당자, 인증 등급 |
| 스키마 | 컬럼명, 타입, 설명 |
| 샘플 | 실제 데이터 미리보기 (PII 마스킹). **별도 권한 필요** |
| 계보 | 상·하위 흐름 DAG |
| 품질 | DQ 규칙 결과, Trust Index |
| 태그/용어 | 태그 목록, 용어집 연결 |

**인라인 즉시 적용 편집**:

| **기능** | **방식** |
| --- | --- |
| 도메인 지정 | 계층형 트리 탐색 + 실시간 검색. 클릭 즉시 적용 |
| Tier (중요 등급) | Tier 1~5 단일 선택 팝오버. 즉시 반영 |
| 인증 등급 | Gold/Silver/Bronze 팝오버. 즉시 반영 |
| 태그 | 다중 선택. 배타적 태그 충돌 시 경고 |
| 담당자 (Owner) | 사용자 검색 후 선택 |
| 설명 | 인라인 텍스트 편집 |

---

### 5.6 데이터 계보 (FR-LIN)

**화면 목적**: 데이터 출처·하류를 DAG로 시각화
**URL**: `/lineage?view=service|domain|dataProduct`

| **기능** | **상세** |
| --- | --- |
| 플랫폼 계보 시각화 | Dagre 기반 DAG 렌더링 |
| 뷰 선택 | Service / Domain / DataProduct 3가지 관점 |
| 풀스크린 모드 | 전체 화면 계보 탐색 |

**계보 레벨**: 테이블 / 컬럼 / 파이프라인

### 5.10 데이터 품질 (FR-DQ)

**화면 목적**: 데이터 신뢰도 수치화 및 관리
**URL**: `/quality/:tab?`

**Trust Index 공식**:

```
Data Trust Index = (DQ Score × 0.6) + (메타데이터 충실도 × 0.2) + (활용도 × 0.2)
```

| **구성 요소** | **가중치** | **담당** |
| --- | --- | --- |
| DQ Score | 60% | 자동 (완전성·정확성·일관성·신선도, Great Expectations 자동 검증) |
| 메타데이터 충실도 | 20% | **수동 — 기획자/데이터 오너 작업** |
| 활용도·안정성 | 20% | 자동 (정시 수집률·쿼리 빈도·장애 이력) |

**인증 등급**:

| **Trust Index** | **등급** | **Tier** | **접근 대상** |
| --- | --- | --- | --- |
| 90 이상 | Gold | 1~2 | 공장장·현장 반장. 모바일 알림 연동 |
| 70~89 | Silver | 3 | 해당 공정 엔지니어·설비보전원 |
| 70 미만 | Bronze | 4 | 데이터 엔지니어·인프라 관리자만 |

> **기획자 주의**: 파이프라인 레이어(Bronze/Silver/Gold)와 인증 등급(Bronze/Silver/Gold)은 별개 개념. **Gold 인증 유지 조건: Trust Index 90점 이상. 미달 시 Gold → Silver 자동 강등.**

## 8. UX 설계 원칙 & 공통 정책

### 8.1 설계 원칙 1: 즉시 적용형 (Immediate Apply) — "저장 버튼은 없다"

```
사용자 클릭
  → [로딩 스피너 표시]
  → 성공: Toast "저장되었습니다" + 화면 값 갱신
  → 실패: Toast "저장에 실패했습니다" + 기존 값으로 자동 복원(Rollback)
```

새 편집 모달/팝오버를 만들 때 이 3단계 흐름이 명세에 반드시 포함되어야 한다.

### 8.2 설계 원칙 2: 독립적인 위젯 상태 관리 — "한 위젯이 죽어도 나머지는 살아있다"

신규 위젯 기획 시 반드시 4단계 상태를 모두 설계해야 한다.

| **단계** | **화면 표현** |
| --- | --- |
| Loading | Skeleton Screen 또는 중앙 스피너 |
| Result | 정상 데이터 렌더링 |
| Empty | "아직 데이터가 없습니다" 전용 안내 문구 + 다음 액션 유도 |
| Error + Retry | 에러 아이콘 + 실패 안내 + [다시 시도] 버튼 (해당 API만 재호출) |

### 8.3 설계 원칙 3: 태그 상호 배타성 검증 — "모순 태그는 시스템이 사전 차단"

같은 Classification 그룹에서 충돌하는 태그(예: `극비` + `일반 공개`)가 동시에 선택되면 차단.
`mutuallyExclusive=true` 속성 적용.

* **대안 A (자동 스위칭)**: 새 태그 선택 시 기존 태그 자동 해제 ← **현재 미결**
* **대안 B (팝업 차단)**: 경고 팝업으로 저장 강제 반려 ← **현재 미결**

### 8.4 공통 UX 정책 세부 규칙

| **정책** | **규칙** |
| --- | --- |
| 말줄임 + 툴팁 | 컨테이너 너비 초과 시 `...` 처리. 호버 **150ms 딜레이** 후 툴팁 노출. 배지(Badge)는 툴팁 제외 |
| 페이지네이션 | 기본 10개/페이지. 드롭다운 20/50/100 선택. **탭 전환 후 돌아와도 페이지·개수 상태 유지** |
| 개별 재시도 | API 실패 시 해당 영역만 [다시 시도]. 페이지 전체 새로고침 없음 |
| 숫자 축약 | 1,000 → `1k`, 1,000,000 → `1M`. 소수점 1~2자리 절사 |
| URL 상태 동기화 | 검색어·필터 조건은 URL에 반영. 링크 공유 시 동일 결과 재현 |
| 결과 0건 처리 | 필터 초기화 옵션 제공 |

### 8.5 즉시 적용 vs 저장 버튼 판단 기준

| **즉시 적용** | **저장 버튼** |
| --- | --- |
| 단일 필드 변경 (도메인, Tier, 인증등급, 태그) | 복수 필드 동시 변경 (Connector 생성, DAG 생성, Run 생성) |
| 취소해도 데이터 손실 없음 | 중간 저장 필요 (코드 편집) |
| 롤백 자동 처리 가능 | 사용자가 변경 의도를 확인해야 하는 경우 |

### 8.6 UI Enable/Disable vs Active/Inactive

| **구분** | **Enable/Disable** | **Active/Inactive** |
| --- | --- | --- |
| 의미 | "쓸 수 있는가?" | "지금 쓰고 있는가?" |
| 제어 주체 | 시스템 조건 | 사용자 Interaction |
| UI 표현 | Grey-out / Dimmed | Highlight / color |

| **문제** | 데이터 거버넌스 작업(태그 지정, 도메인 매핑 등)은 건당 수초~수분 단위의 빈번한 소규모 편집. 매번 저장 버튼 클릭 → 병목 발생 |
| **선택** | 클릭 즉시 API 전송. 실패 시 자동 Rollback + Toast 알림 |
| **트레이드오프** | ✅ 거버넌스 작업 속도 대폭 향상 |
| | ❌ 실수 클릭 시 즉시 적용. Undo 기능 부재. 네트워크 불안정 환경에서 Rollback 빈도 증가 |

### 결정 3: RBAC + ABAC 이중 접근 제어 구조

| **항목** | **내용** |
| --- | --- |
| **문제** | RBAC만으로는 "같은 역할이지만 특정 자산(국가핵심기술, PII)은 차단"이 불가. ABAC만으로는 역할별 기능 제어가 복잡해짐 |
| **선택** | RBAC(역할 기반) = 기능 접근 제어. ABAC(태그 기반) = 데이터 자산 접근 제어. 두 체계를 계층 구조로 결합 |
| **트레이드오프** | ✅ 세밀한 보안 제어 가능. 국가핵심기술·PII 자동 마스킹 |
| | ❌ 설계 복잡도 증가. 권한 정책 관리 난이도 상승 |

### 결정 4: Phase 1 공급사 구축형 → Phase 2 수요사 편집형 (Low/No-Code) 전환

| **항목** | **내용** |
| --- | --- |
| **문제** | Phase 1에서 원프레딕트가 고객사 환경을 직접 Hard-Coding으로 구축 → 확장성 한계, 고객 의존성 심화, 납품마다 개발 리소스 소모 |
| **선택** | Phase 2에서 고객이 UI에서 직접 도메인·태그·커넥터·파이프라인을 설정하는 플랫폼으로 전환 |
| **트레이드오프** | ✅ 고객 자립성 확보. 납품 리소스 감소. 진정한 플랫폼 비즈니스 모델 가능 |
| | ❌ UI 복잡도 급증. Phase 2 개발 범위 방대. 비기술자 고객의 러닝커브 상승 |
| **기획자 주의** | 모든 기획을 **"고객이 UI에서 직접 설정할 수 있는가?"** 기준으로 검토 |

### 결정 5: MSA 구조 + Must vs Optional 분리

| **항목** | **내용** |
| --- | --- |
| **문제** | 고객사 인프라 환경이 제각각. Kafka가 있는 곳도 없는 곳도 있음. 모든 컴포넌트를 필수로 하면 도입 장벽 폭증 |
| **선택** | Kubernetes·Kafka·OpenMetadata·Iceberg 등 핵심만 Must. CDC·Superset·Gitea 등은 Optional로 분리. 고객 환경에 따라 선택 가능 |
| **트레이드오프** | ✅ 고객사 환경 적응력 향상. 납품 유연성 |
| | ❌ Optional 조합에 따른 테스트 케이스 폭발적 증가. QA 부담 상승 |

## 13. PM 기획 체크리스트

### 화면·기능 범위

```
□ 어느 FR/KF 화면에 영향을 주는가?
□ 레이아웃 패턴 4가지 중 어느 것을 사용하는가? (Global / Search / Detail / Code Editor)
□ 위젯 4가지 상태(Loading / Result / Empty / Error)를 모두 설계했는가?
□ 즉시 적용인가, 저장 버튼이 필요한가?
□ "고객이 UI에서 직접 설정할 수 있는가?" 기준으로 검토했는가? (결정 4)
```

### 권한·보안

```
□ 어떤 RBAC 역할이 사용하는가? (System Admin / Domain Admin / Member / Viewer)
□ ABAC 태그 상태에서도 정상 작동하는가? (PII 마스킹, 대외비 숨김)
□ URL 직접 접근 시 권한 없는 사용자 처리 방식은?
□ 감사 로그에 기록해야 하는 액션인가?
□ Admin 전용인가, 일반 사용자도 접근 가능한가?
```

### 데이터 정합성

```
□ Trust Index에 영향을 주는가? (어떤 구성 요소를 변경하는가?)
□ Lineage에 새로운 노드/엣지가 생기는가?
□ 다른 화면과 실시간 동기화가 필요한가?
□ 숫자 값이 있다면 단위 축약(k/M/G) 및 소수점 처리 규칙을 정의했는가?
```

### 에러·예외 처리

```
□ 필수 입력 누락 시 처리 방식? (Toast / 필드 붉은 처리 / 버튼 비활성화)
□ 서버 오류 시 처리 방식? (자동 롤백 / 재시도 버튼)
□ 빈 상태(Empty)에서 사용자에게 어떤 안내와 다음 액션을 제공하는가?
```

### 오픈소스 연동 확인

```
□ 신규 기능이 OpenMetadata·Airflow·MLflow 중 하나와 연관되는가?
□ 해당 오픈소스의 기능 한계를 개발팀과 사전 확인했는가? (결정 1)
□ 오픈소스 업그레이드 시 해당 기능에 영향이 있는가?
```
