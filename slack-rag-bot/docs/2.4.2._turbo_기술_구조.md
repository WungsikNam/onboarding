# 2.4.2. turbo 기술 구조

이 문서는 Guardian Turbo의 **기술 구조**를 다룹니다. 데이터가 어떻게 흐르는지, 각 분석 방법이 기술적으로 무엇인지, PDX에서 재현하려면 무엇이 필요한지를 중심으로 작성되었습니다.

## 1. 시스템 전체 데이터 흐름

```
[현장 설비: 가스터빈 · 압축기 · 증기터빈]
    ↓  진동(X/Y/Z), 온도, 압력, RPM 등
[OPC-UA / OPC-DA 서버 (DCS 연결)]
    ↓
[Collector (현장 서버, 원프레딕트 설치)]
  · OPC-UA: 안정적, 구독(Subscribe) 방식
  · OPC-DA: COM/DCOM 기반, 폴링(Polling) 방식 → 가용성 이슈 원인
    ↓
[ClickHouse (시계열 OLAP DB)]
  · float_signals          : 단일 실수값 (온도·압력·RMS 등)
  · float_array_signals    : 배열 데이터 (Spectrum 파형 등)
  · coordinate_signals     : 2D 좌표 단일값 (베어링 중심점)
  · coordinate_array_signals: 2D 좌표 배열 (Orbit 궤적)
  · symbol_signals         : 상태 코드
  · text_signals           : 텍스트 진단 결과
    ↓
[AI 진단 엔진]
  · 15 fault mode 리스크 스코어 산출
  · 채널 30만번대에 결과 저장
    ↓
[Backend API]
    ↓
[Frontend — Scene JSON 기반 렌더링]
  · 각 화면 = sceneId에 대응하는 JSON 파일
  · 픽셀 좌표 기반 오버레이
```

## 2. 데이터 수집 레이어 — OPC-UA vs OPC-DA

* 산업 자동화에서 설비·센서 데이터를 주고받기 위한 **통신 표준 프로토콜**

    * OT 커넥터(데이터 수집 레이어)가 현장 설비로부터 데이터를 가져올 때 이 프로토콜을 사용
    

| **항목** | **OPC-UA** | **OPC-DA** |
| --- | --- | --- |
| 표준 연도 | 2008\~, 현대 표준 | 1996\~, 레거시 |
| 기반 기술 | TCP/IP, 플랫폼 독립 | Windows COM/DCOM 의존 |
| 수집 방식 | Subscribe (변화 시 푸시) | Polling (주기적 요청) |
| 보안 | TLS 암호화, 인증 내장 | Windows 인증 의존 |
| 가용성 | 안정적 | COM 프로세스 크래시 → 수집 중단 반복 |
| 현장 현실 | 신규 설비, 최근 DCS 업그레이드 사이트 | 구형 DCS 여전히 다수 운영 중 |

**OPC-DA 가용성 이슈 5가지 유형**  
 ① COM 서버 프로세스 비정상 종료 ② DCOM 보안 설정 변경으로 접속 차단 ③ Windows 업데이트 후 COM 등록 깨짐 ④ 네트워크 세그먼트 변경으로 DCOM 포트 차단 ⑤ 메모리 누수로 인한 장시간 운전 후 수집 지연  
 → 신규 사이트는 OPC-UA 우선 협의 필수

## 3. 분석 방법론 기술 원리

### 3.1 FFT (Fast Fourier Transform) — Spectrum 분석

* 시간 도메인의 진동 신호를 주파수 도메인으로 변환. 각 주파수 성분의 에너지를 분리하여 고장 "지문"을 찾는다.

| **주파수 성분** | **의미하는 고장** |
| --- | --- |
| 1x RPM | 언밸런스 (Unbalance) |
| 2x RPM | 미스얼라인먼트 (Misalignment) |
| 0.42\~0.49x RPM | 오일 훨 (Oil Whirl) — 유막 불안정 |
| 0.5x RPM | 오일 훨 고착 (Oil Whip) |
| BPFO = (N/2) × RPM × (1 - d/D×cosα) | 베어링 외륜 결함 (Outer Race) |
| BPFI = (N/2) × RPM × (1 + d/D×cosα) | 베어링 내륜 결함 (Inner Race) |

**구현 필수항목**  
 · ClickHouse 테이블: float_array_signals (채널 10만번대)  
 · 1x/2x 마커 자동 표시: RPM 채널(20만번대)에서 현재 RPM 읽어 계산  
 · X축 단위: Hz 또는 Order(배수) — 고객사 선호에 따라 전환 기능 고려  
 · 다운샘플링 금지: 파형 원본 보존 정책 적용

### 3.2 Waterfall 차트 — 시간/RPM 기반 Spectrum 적층

Spectrum(FFT 결과)을 시간 또는 RPM 순서로 쌓아 3D 시각화. "언제 이 주파수 성분이 나타났는가"를 추적.

* **시간 기반 Waterfall**: 정상 운전 중 주파수 성분 추이 모니터링
* **RPM 기반 Waterfall**: 기동·정지 중 공진 주파수 위치 확인 (Critical Speed 파악)

**구현 필수항목**  
 · 시계열 Spectrum 데이터: float_array_signals 복수 시점 조회  
 · 다운샘플링 없는 원본 Spectrum 필요 (압축 시 고주파 정보 손실)  
 · 3D 표면 렌더링: WebGL 기반 라이브러리 필요 (Three.js 등)  
 · RPM 기반 모드: RPM 채널과 시간 동기화 필수

### 3.3 3D Orbit — 축 궤적 분석

X방향 변위 센서 + Y방향 변위 센서(90도 위상차로 설치) 신호를 동시에 플롯 → 축의 2D 궤적을 그린다. 시간 축을 추가하면 3D Orbit.

| **궤적 형태** | **의미** |
| --- | --- |
| 원형 | 정상 (균형 잡힌 회전) |
| 8자형 | 오일 훨 (Oil Whirl) 의심 |
| 한쪽으로 쏠린 타원 | 미스얼라인먼트 방향 추정 가능 |

**ISO 7919-3 임계값 (회전체 축 진동)**

| **Zone** | **진폭 (peak-to-peak)** | **의미** |
| --- | --- | --- |
| A | ≤ 25 μm | 신규 설비 정상 범위 |
| B | ≤ 50 μm | 장기 운전 허용 범위 |
| C | ≤ 100 μm | 제한적 운전, 점검 필요 |
| D | > 100 μm | 즉시 조치 필요 |

**베어링 간극 비율**: 설계 베어링 간극 대비 실측 중심 변위 — <30%=정상, 30\~50%=경고, >50%=알람

**구현 필수항목**  
 · ClickHouse 테이블: coordinate_array_signals (채널 10만번대 XY 쌍)  
 · X/Y 센서 위상 정보 메타데이터 필요 (CW/CCW 회전 방향에 따라 궤적 방향 결정)  
 · 베어링 간극값(shaft_center_offset): 현장 실측 후 시스템에 입력 필수  
 · ISO Zone 색상 오버레이: 배경 원 3개 (25/50/100 μm 반경)

### 3.4 Shaft Centerline — 베어링 중심 이동 추적

베어링 내에서 축 중심 위치의 시간에 따른 변화를 추적. 윤활 상태, 베어링 마모 진행을 시각화.

**구현 필수항목**  
 · 베어링 간극 설계값: 반드시 현장에서 실측 및 입력  
 · 채널: coordinate_signals (단일 XY 좌표값, 시계열)

## 4. ClickHouse DB 구조 및 Channel ID 체계

* ClickHouse는 **컬럼 기반(Columnar) 오픈소스 OLAP 데이터베이스**로, 대규모 데이터의 실시간 분석 쿼리에 특화된 DB입니다.

### 4.1 ClickHouse 선택 이유

* **컬럼형 저장**: 특정 채널의 시계열 조회가 매우 빠름 (행형 DB 대비 10\~100배 빠른 집계)
* **높은 압축률**: 시계열 데이터의 연속된 유사값 → 압축률 높음
* **대용량 처리**: 수십만 채널 × 연도 단위 데이터를 실시간 조회 가능

### 4.2 테이블 타입별 용도

| **테이블 타입** | **저장 데이터** | **대표 채널** |
| --- | --- | --- |
| float_signals | 단일 실수값 (온도, RPM, RMS 진동) | 0\~8만, 20만번대 |
| float_array_signals | 실수 배열 (FFT Spectrum, 시간 파형) | 10만번대 |
| coordinate_signals | 2D 좌표 단일값 (베어링 중심점) | 10만번대 XY쌍 |
| coordinate_array_signals | 2D 좌표 배열 (Orbit 궤적) | 10만번대 XY쌍 |
| symbol_signals | 상태 코드 (정상/경고/이상) | 30만번대 |
| text_signals | 텍스트 진단 결과 | 30만번대 |

### 4.3 Channel ID 6자리 체계

| **범위** | **의미** | **예시** |
| --- | --- | --- |
| 000000\~089999 | 공정 데이터 (DCS: 온도·압력·유량) | 010001 = GT1 입구온도 |
| 100000\~199999 | 동적 진동 파형 데이터 | 100102 = GT1 베어링#1 XY Orbit |
| 200000\~299999 | 정적 기준값 (RPM, 기준 진동값 등) | 200100 = GT1 RPM |
| 300000\~399999 | AI 진단 결과 (Fault Mode 리스크 스코어) | 300011\~300024 = 15 fault modes |

## 5. Scene JSON 구조 (화면 구성 메커니즘)

```json
{
  "sceneId": 5,
  "elements": [
    {
      "type": "RPM",
      "layout": {"top": "340px", "left": "120px"},
      "rpm": {"channelId": 200100}
    },
    {
      "type": "BearingStatus",
      "layout": {"top": "210px", "left": "450px"},
      "status": {"channelId": 300100},
      "isoLevel": {"channelId": 300101}
    },
    {
      "type": "VibrationOrbit",
      "layout": {"top": "400px", "left": "800px"},
      "vibXY": {"channelId": 100102}
    }
  ]
}
```

### Scene ID 매핑

| **sceneId** | **화면** |
| --- | --- |
| 5 | 메인 대시보드 (설비 사진 오버레이) |
| 9 | 디지털 트윈 (3D 모델 오버레이) |
| 13\~18 | 베어링 카드 (베어링 번호별 상세) |

**PDX 재현 시 이 구조의 문제점**  
 · top/left가 픽셀 절대값 → 화면 크기 변경 시 레이아웃 깨짐  
 · JSON 파일 직접 편집 필요 → 관리자 UI 없음  
 · 신규 사이트 납품 시 개발자 3\~5일 투입 필요  
 → PDX에서는 상대좌표(%) + 관리자 드래그앤드롭 UI로 전환 목표

## 7. Cyclone 연계 현황 및 통합 경로

**현재 상태: 미연결**  
 Guardian Turbo는 ClickHouse 기반 독립 스택으로 운영되며, Cyclone(Iceberg+Ceph+Kafka)과 현재 연결되어 있지 않다.

| **항목** | **Guardian Turbo** | **Cyclone** |
| --- | --- | --- |
| 운영 DB | ClickHouse (OLAP) | Apache Iceberg (Data Lake) |
| 스트리밍 | Collector (자체 개발) | Kafka |
| Object Storage | 해당 없음 | Ceph |
| 메타데이터 관리 | 없음 | OpenMetadata |

### 통합 가능 경로 (미구현)

1. **ClickHouse Connector 방식**: Cyclone에 ClickHouse 커넥터 추가 → Turbo 데이터를 Cyclone 카탈로그에 메타데이터로 등록. 데이터 이동 없이 조회만 연결.
2. **Collector → Kafka 전환**: Turbo의 데이터 수집 계층을 Kafka로 교체 → Cyclone의 Ingestion 파이프라인에 자연스럽게 통합. 구조적 변경이 크지만 장기적으로 단일 플랫폼 가능.
