## 1. 제품이 존재하는 이유 — 왜 만들었는가

### 1.1 어떤 문제를 해결하는가

산업용 전동기(모터)는 공장에서 펌프·컴프레서·팬을 돌리는 핵심 설비다. 대형 공장은 수백\~수천 대의 모터를 운영한다.

| 기존 방식 | 남는 문제 |
| --- | --- |
| 현장 수동 점검 (소음·진동·온도 측정) | 모터 한 대씩 직접 확인 → 수백 대 규모에서 인력·시간 한계 |
| 사후 대응 (고장 후 교체) | 생산 라인 중단, 긴급 교체 비용 발생 |
| 정기 점검 스케줄 | 점검 사이 구간은 블랙박스 — 이상 감지 불가 |
| 진동 분석 전문가 의존 | 소수 전문가 부재 시 대응 불가, 지식 이전 어려움 |

### 1.2 가디원 모터의 포지셔닝

> **"공장 내 수백 대 모터를 iDAQ 센서와 AI로 실시간 모니터링하고, 고장 전 이상 징후를 자동 진단하는 예지보전 플랫폼"**

| 가치 | 설명 |
| --- | --- |
| **자동 이상 감지** | AI가 전류 신호를 분석하여 이상 모터를 자동으로 찾아냄 |
| **대규모 관리** | 수십\~수백 대 모터를 단일 대시보드에서 일괄 모니터링 |
| **계획 정비** | 고장 전 미리 알려주어 계획적 정비 → 생산 중단 최소화 |
| **에너지 효율** | 이상 모터는 전력 소비 증가 → 조기 교체로 에너지 절감 |

### 1.3 진단 대상 고장 유형

| 고장 부위 | 주요 신호 |
| --- | --- |
| **고정자 (Stator)** | 권선 불량, 절연 열화 |
| **회전자 (Rotor)** | 봉 파손, 편심 |
| **베어링 (Bearing)** | 마모, 윤활 부족 |
| **축 (Shaft)** | 미스얼라인먼트, 언밸런스 |

### 2.1 전체 화면 구조 (IA)

```
Guardian Motor 화면 구조
├── [로그인]
│
└── [메인 대시보드] — 전체 모터 건전성 현황 카드
    │  ├── 정상 / 관찰 / 주의 모터 수 요약
    │  ├── 미확인 알람 배지
    │  └── 정지 / 학습 중 모터 별도 표시
    │
    ├── [모터 목록] — 설비별 상태 리스트
    │
    └── [모터 상세] — 개별 모터 상세 분석
         ├── [시점 분석] — 특정 시점의 진단 결과
         │    ├── 진단 등급 (정상/관찰/주의)
         │    ├── 부위별 건전성 지수 (고정자/회전자/베어링/축)
         │    └── 판단 근거 Feature 표시
         │
         ├── [트렌드 분석] — 시계열 건전성 변화 추이
         │    ├── 건전성 지수(HI) 트렌드 그래프
         │    └── 부위별 분리 트렌드
         │
         ├── [엔지니어링] — 전문가용 Feature 데이터 조회
         │    ├── Feature 리스트 및 시계열 그래프
         │    ├── FFT 주파수 차트 (1x~5x)
         │    └── 알고리즘 파라미터 수정
         │
         └── [알람 이력] — 발생 알람 목록

[관리자 메뉴]
    ├── [계정 및 권한 설정]
    └── [설비 정보 관리]
```

### 2.2 주요 사용자 흐름

#### 흐름 A: 일상적인 모터 건전성 모니터링 (가장 빈번)

```
로그인 → 메인 대시보드
  → 전체 모터 상태 카드 확인
  → 노란/빨간 카드 발견 시 해당 모터 클릭
  → 시점 분석: 어떤 부위가 이상인지 확인
  → 트렌드 분석: 이전부터 악화 추세인가? 갑자기 발생?
  → 조치 결정 (관찰=모니터링 주기 단축 / 주의=현장 점검 의뢰)
```

#### 흐름 B: 알람 발생 후 대응

```
상단 알림 아이콘(빨간 배지) 클릭 → 알람 목록 모달
  → 알람 클릭 → 알람 발생일 기준 날짜로 자동 이동
  → 시점 분석: 어떤 부위, 어떤 Feature가 원인?
  → 트렌드 분석: 언제부터 악화?
  → 엔지니어링 탭: Feature 데이터 상세 검토 (전문가)
  → 유지보수 팀에 점검 요청
```

#### 흐름 C: 신규 모터 등록 및 초기 설정

```
관리자 계정 로그인
  → 설비 정보 입력 (모터명, 정격 전류, 극수, 베어링 타입)
  ⚠️ 24 pole 이상, 슬리브 베어링은 적용 제약 반드시 확인
  → iDAQ 센서 연동 확인 (데이터 수신 여부)
  → 초기 데이터 학습 시작 → "학습 중" 상태 표시
  → 학습 완료 후 실제 진단 시작
```

#### 흐름 D: False Positive 발생 시 대응

```
알람 과다 발생 모터 목록 추출
  → 엔지니어링 탭에서 Feature 데이터 확인
  → 원인 분석 (운전 조건 변화? 센서 노이즈? 파라미터 부적합?)
  → 알고리즘팀과 협의: 파라미터 조정 또는 Feature 추가
  → 단기 조치: "학습 중" 상태로 마스킹 → 고객사 노출 방지
```

## 5. 핵심 설계 및 의사결정 히스토리 (Decision Making History)

각 항목은 "어떤 문제가 있었고 → 왜 이 방식을 선택했고 → 어떤 대안이 있었는가"를 역추적합니다.

### 5.1 전류(Current) 기반 진단 — 왜 진동이 아닌 전류인가

**문제**: 진동 센서 기반 진단(가디원 터보 방식)은 모터마다 센서를 물리적으로 부착해야 한다. 수백 대 모터가 있는 공장에서는 설치 비용이 선형으로 증가한다.

**선택**: 모터가 이미 연결된 전력 케이블에서 전류(Current)를 측정. 전류 신호에는 모터 고장 정보가 인코딩되어 있다(Motor Current Signature Analysis, MCSA). iDAQ 센서 1대가 3상 전류(U/V/W)를 동시 측정.

**왜 이것이 가능한가**: 모터 고장(베어링 마모, 회전자 봉 파손 등)은 전류 파형의 특정 주파수 성분에 고장 지문을 남긴다. 이 성분을 FFT로 추출하면 진동 센서 없이도 진단 가능.

**트레이드오프**: 진동 센서보다 설치가 간편하고 비용이 낮으나, 24 pole 이상 고극수 모터나 슬리브 베어링 모터에서는 진단 정확도가 제한된다. 적용 범위에 한계가 있음.

### 5.2 건전성 지수(HI) 3단계 등급 — 왜 더 세분화하지 않았는가

**문제**: 진단 결과를 수치(0\~100)로만 표시하면 현장 담당자가 "얼마나 심각한가"를 판단하기 어렵다. 반면 너무 세분화하면 등급 경계에서 혼란 발생.

**선택**: 정상(HI > 80) / 관찰(50\~80) / 주의(HI < 50) 3단계. 현장 담당자가 즉각 행동 여부를 판단할 수 있는 최소 단위.

**트레이드오프**: 단순하여 직관적이나, "관찰 등급이 80에 가까운지 50에 가까운지"에 따라 긴급도가 다른데 이를 표현하지 못한다. HI 수치를 함께 표시하는 것으로 보완.

### 5.3 엔지니어링 화면 (Feature 시각화) 추가 — 왜 만들었는가

**문제**: SK에너지 PM들이 "진단 방식을 이해할 수 없다"며 알고리즘 공개 요청 반복 → AI 결론만 보여주는 구조에서 현장 전문가 신뢰 구축 실패.

**선택**: 진단에 사용된 Feature 데이터를 그래프로 직접 보여주는 엔지니어링 탭 추가. "AI가 이 Feature의 이 수치를 보고 이상이라고 판단했다"는 근거 제공.

**가디원 터보와의 공통점**: 터보에서 3D Orbit/Waterfall이 "AI 결론 말고 원시 데이터를 직접 보겠다"는 니즈에 대응했던 것과 동일한 패턴. 산업 현장 전문가는 블랙박스 AI를 신뢰하지 않는다는 교훈의 반복.

**트레이드오프**: 전문가 신뢰는 높아졌으나, 비전문가에게는 오히려 혼란을 줄 수 있는 화면. 일반 사용자와 전문가 사용자 분리가 필요해진 계기.

### 5.4 딥러닝 기반 Slip 추정 도입 (v1.11.0) — 왜 교체했는가

**문제**: 전류 기반 진단의 핵심은 회전 주파수 정확히 알아내는 것(Slip 추정)이다. 기존 규칙 기반 Slip 추정이 부정확한 경우 정상 모터에 이상 알람 발생(False Positive) 직결.

**선택**: 규칙 기반 Slip 추정 → 딥러닝 모델로 교체. 다양한 운전 조건에서도 정확한 회전 주파수 추정 가능.

**효과**: FP(오탐) 감소, 진단 정확도 향상. Motiva(미국) 납품 대비로 도입 타이밍이 결정됨.

### 5.5 "학습 중" 상태 마스킹 — 왜 이 방식인가

**문제**: LLDPE 사이트에서 FP(오탐)가 과다 발생. 알고리즘 재학습 기간 동안 결과를 고객사에 그대로 노출하면 신뢰도 치명타.

**선택**: 재학습 기간 동안 해당 모터에 "학습 중" 상태 표시 → 고객사에 결과 미노출. 알고리즘 수정 완료 후 정상 진단 재개.

**트레이드오프**: 고객 신뢰 보호에 효과적이나, "학습 중"이 너무 길어지면 "이 제품이 실제로 작동하는가"에 대한 의문 유발. 마스킹은 임시 해결책이며 근본적 FP 방지가 우선.

### 5.6 On-Premises 지원 (v1.12.1) — 왜 필요했는가

**문제**: SK에너지, GS칼텍스, 한화토탈에너지스 등 대기업 고객들의 데이터 보안 정책상 외부 서버로 데이터 전송 불가. SaaS 전용 제품으로는 대기업 시장 진입 차단.

**선택**: 동일 코드베이스를 On-Premises 환경에서도 동작하도록 개선. 데이터는 고객사 내부 서버에 저장, 원프레딕트는 제품만 공급.

**트레이드오프**: 대기업 시장 공략 가능해졌으나, SaaS 대비 운영·유지보수 비용 증가. 이메일 알람 등 클라우드 의존 기능 비활성화 필요.

### 5.7 이중 베어링 모터 지원 (v1.10.0) — 왜 필요했는가

**문제**: 로템SRS, GS칼텍스 일부 모터가 이중 베어링(Double Bearing) 구조. 기존 단일 베어링 알고리즘으로는 커버리지 확보 불가.

**선택**: 이중 베어링 모터 전용 Feature 추출 및 진단 로직 추가. v1.10.0 릴리즈로 로템SRS, GS칼텍스 커버리지 완전 확보.

## 8. 레슨런 (Lessons Learned)

SK에너지 PM들의 알고리즘 공개 요청이 반복됐다. 엔지니어링 화면(Feature 시각화)을 추가한 이후 신뢰도가 개선됐다. **AI 결론을 보여주는 것보다 AI 근거를 보여주는 것이 신뢰 구축의 핵심이다.** 가디원 터보(3D Orbit/Waterfall)와 동일한 교훈.

24 pole 이상 모터 적용 제약을 사전에 고객사에 공지하지 않아 HOU 사이트에서 반복 오류가 발생했다. 이후 기술 규격서에 명시하는 것으로 개선됐다. **제품이 안 되는 것을 명확히 하는 것이 신뢰 관리의 일부다.**

LLDPE 사이트에서 FP 과다 발생 → "학습 중" 마스킹으로 임시 대응. 마스킹은 영리한 단기 해결책이지만 FP 자체를 줄이는 근본적 접근이 우선이다. 설비 고장을 감지해주는 제품이 정상 설비에 계속 알람을 발생시키면 제품에 대한 신뢰가 영구적으로 훼손된다.

국내에서 "내부 설비팀이 직접 모니터링"하는 운영 방식을 미국에 그대로 적용했으나, 미국은 설비 관리를 MRO 업체에 외주 위임하는 구조라 수요자가 달랐다. PMF 탐색 없이 제품을 그대로 들고 가면 시장 미스매치가 발생한다.

SK에너지(300대)와 GS칼텍스(150대)가 전체의 73%를 차지한다. 이 두 고객사의 재계약 여부가 사업 존립과 직결되는 구조. 가디원 터보의 GS Caltex 의존과 동일한 패턴. 레퍼런스 고객은 소중하지만, 다변화가 없으면 성장 한계와 리스크가 동시에 온다.

이메일 알람처럼 클라우드를 전제로 설계된 기능은 On-prem 전환 시 비활성화될 수 있다. 고객사에 On-prem 납품 시 "이 기능은 On-prem에서 제약이 있다"는 사전 협의가 없으면 계약 후 분쟁 발생 가능.
