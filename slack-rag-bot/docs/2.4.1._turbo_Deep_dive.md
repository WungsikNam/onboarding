## 1. 제품이 존재하는 이유 — 왜 만들었는가

### 1.1 출발점: 가스 터빈은 왜 특별한가

가스터빈·증기터빈·압축기는 산업 설비 중 **단위 고장 비용이 가장 높은 설비**다.

* 대형 발전소 가스터빈 1대 비계획 정지 손실: 수억\~수십억 원/일
* 정기 분해 검사(OH) 주기: 24,000\~48,000 운전시간 → 조기 이상 감지로 주기 최적화 가능
* 고속 회전체 특성상 이상 진행 속도 빠름 → 연속 모니터링 필수

### 1.2 기존 시장의 공백

| **기존 상황** | **남는 문제** |
| --- | --- |
| OEM 자체 모니터링 (GE Mark, Siemens T3000 등) | 벤더 종속, 타 설비와 통합 불가 |
| DCS/SCADA 경보 시스템 | 임계치 초과 후 알람 → 예방 불가 |
| 진동 전문가 현장 점검 | 비정기적, 주관적 판단, 비용 높음 |
| 글로벌 솔루션 (Bently Nevada, SKF) | 고가, 국내 환경 커스터마이징 어려움 |

**가디원 터보의 포지셔닝**: "AI 기반 진동 분석 + 현장 친화적 시각화"로 이 공백을 공략.

## 2. 제품 IA와 사용자 흐름

### 2.1 전체 화면 구조 (IA)

```
G.Turbo 화면 구조
├── [로그인]
│
└── [메인 화면] — 전체 설비 카드 목록
    │  ├── 이미지 모드: 설비 일러스트 + 상태 색상
    │  └── 카드 모드: 텍스트/수치 리스트
    │
    ├── [대시보드] — 개별 설비 상세 모니터링 (핵심 화면)
    │    ├── 트레인 기본 정보 (공정명·설비명·번호)
    │    ├── 운전 정보 게이지 (RPM, Power)
    │    ├── 스러스트 베어링 게이지
    │    ├── 설비 이미지 + 베어링 상태 오버레이
    │    ├── 3D Orbit 플롯
    │    ├── 고장 모드별 위험도 (15개 막대)
    │    ├── 알람 내역
    │    └── 태그 리스트
    │
    ├── [진동 디지털 트윈] — 전체 베어링 Orbit 비교
    │    ├── 실시간 / 기간 탭
    │    ├── RPM 트렌드
    │    ├── 전체 베어링 3D Orbit
    │    ├── 베어링 정보 카드 (Vib/Phase/Temp)
    │    └── 선택 베어링 상세 (Orbit/Spectrum/Polar/Shaft Centerline)
    │
    ├── [트렌드 조회] — 시계열 센서값 차트
    │    ├── 실시간 조회 탭
    │    └── 기간 조회 탭
    │
    ├── [데이터 조회] — 전문가용 분석 화면
    │    ├── Overview 탭 (전체 베어링 한 페이지)
    │    ├── Orbit 탭
    │    ├── Spectrum 탭 (FFT)
    │    ├── Polar/Bode 탭
    │    ├── Shaft Centerline 탭
    │    └── Waterfall 탭
    │
    ├── [진단 보고서] — 일일/시점 보고서
    │    └── PDF 다운로드
    │
    └── [태그 설정] — 관리자용
         ├── 태그 정보 조회/수정
         ├── 알람 임계값 수정
         └── 변경 이력 조회
```

### 2.2 주요 사용자 흐름

#### 흐름 A: 일상적 모니터링 (가장 빈번)

```
메인 화면 → 비정상 카드 색상 확인
  → 대시보드 클릭
  → 고장 모드 막대그래프로 "무엇이 올라갔는가" 파악
  → 데이터 조회 → Spectrum: 어떤 주파수 성분?
  → Waterfall: 언제부터 나타났는가?
  → 3D Orbit: 궤도 형상 확인
  → 조치 결정 (모니터링 지속 / 점검 주기 단축 / 즉시 운전 중단)
```

#### 흐름 B: 알람 발생 후 원인 분석

```
알람 아이콘 클릭 → 알람 목록 모달
  → 발생 시점으로 이동
  → Spectrum → 고장 주파수 식별 (1x=불평형, 0.5x=오일훨, BPFO=베어링)
  → Waterfall → 발생 시점 소급 확인
  → 3D Orbit → Zone D 진입 여부, 8자 형상 여부 확인
  → 원인 분류 후 조치
```

#### 흐름 C: 보고서 작성

```
진단 보고서 화면
  → 날짜/시점 선택
  → 베어링 정보, 고장 모드, 판단 근거 차트 확인
  → PDF 다운로드 (파일명 규칙 자동 적용)
```

## 4. 화면별 정책 및 공통 정책

### 4.1 베어링 상태 표시 정책

모든 화면에서 베어링 상태는 30만번대 채널의 상태값으로 결정된다.

| **상태값** | **채널값** | **색상** | **의미** |
| --- | --- | --- | --- |
| 정상 (Normal) | 0 | 초록 | 정상 운전 범위 내 |
| 주의 (Warning) | 1 | 노랑 | 모니터링 강화 필요 |
| 위험 (Danger) | 2 | 빨강 | 즉시 조치 필요 |

### 4.2 진동 판정 기준 (ISO 7919-3)

아래 기준은 국제 표준(ISO 7919, API 670) 기반의 일반적 가이드입니다. 설비마다 정격 속도·베어링 간극이 달라 절대 기준이 아닙니다. 실제 적용 시 설비 스펙 기준으로 확인 필요.

| **Zone** | **진폭 기준 (3,000 RPM)** | **의미 및 조치** |
| --- | --- | --- |
| **Zone A** | ≤ 25 μm p-p | 신설 설비 기준. 정상. |
| **Zone B** | ≤ 50 μm p-p | 장기 운전 허용 범위. 정상. |
| **Zone C** | ≤ 100 μm p-p | 요주의. 점검 계획 수립. |
| **Zone D** | > 100 μm p-p | 위험. 즉시 조치. |

### 4.3 베어링 간극 비율 정책

| **간극 비율** | **판정** | **설명** |
| --- | --- | --- |
| < 30% | 정상 | 베어링 간극(통상 150\~300 μm) 대비 Orbit 크기 안정 |
| 30 \~ 50% | 주의 | 모니터링 강화 |
| > 50% | 알람 | 베어링 손상 위험. 즉시 점검 고려. |

### 4.4 Orbit 형상 판정 정책

## 5. 핵심 설계 및 의사결정 히스토리 (Decision Making History)

각 항목은 "어떤 문제가 있었고 → 왜 이 방식을 선택했고 → 어떤 대안이 있었는가"를 역추적합니다. 화면·기능·아키텍처 결정을 통합해서 다룹니다.

### 5.1 설비 사진 위 오버레이 대시보드 — 왜 이 방식인가

**문제**: 설비 담당자는 "베어링 #3"이라는 추상적 ID보다 "저 왼쪽 앞 베어링"이라는 공간 인식으로 설비를 이해한다. 숫자·그래프 나열 방식으로는 어디에 문제가 생겼는지 직관적으로 파악하기 어렵다.

**선택**: 실제 설비 사진 위에 센서 데이터를 픽셀 좌표 기반으로 오버레이. 담당자가 화면을 보는 순간 "저기 베어링이 빨간색이다"를 바로 인식 가능.

**기각된 대안**: 리스트형 카드 UI (번호/이름 나열) → 개발은 쉽지만 현장 직관성 낮음.

**트레이드오프**: 시각적 직관성은 높아졌으나, 신규 사이트마다 사진 촬영 → Figma 좌표 추출 → Scene JSON 수동 작성이 필요해졌다. 이것이 납품 구조적 병목의 직접 원인이 되었다.

### 5.2 FFT 기반 Spectrum 분석 — 왜 주파수 도메인인가

**문제**: 진동 신호를 시간 축으로만 보면 "진동이 크다/작다"만 알 수 있다. 언밸런스인지, 미스얼라인먼트인지, 베어링 결함인지 구분이 안 된다.

**선택**: FFT로 주파수 도메인 변환 → 각 고장 유형이 특정 주파수에 "지문(fingerprint)"을 남긴다는 원리 활용.

* 1x RPM 성분 크면 → 언밸런스 의심
* 2x RPM 성분 크면 → 미스얼라인먼트 의심
* 0.42\~0.49x 성분 → 오일 훨(Oil Whirl) 의심
* BPFO/BPFI 성분 → 베어링 외/내륜 결함

**왜 FFT인가 (Wavelet 등 대안 대비)**: 회전체 진동은 주기성이 강하다 → FFT가 가장 해석하기 쉽고, 고장 주파수와 RPM의 관계식이 잘 정립되어 있다. Wavelet은 비주기 과도 신호에 유리하나 회전체 정상 상태 진단에는 FFT가 표준.

### 5.3 Waterfall 차트 — 왜 3D 시간축 적층인가

**문제**: Spectrum(FFT)은 특정 시점의 스냅샷이다. 베어링 결함 주파수가 "지금 있다"는 건 알 수 있지만, "언제부터 생겼는가, 점점 커지는가"는 알 수 없다.

**선택**: Spectrum을 시간순으로 쌓아 3D 시각화 → 특정 주파수 성분의 출현과 성장 추이를 한눈에 파악. RPM 기반 Waterfall도 지원 → 기동·정지 시 공진 주파수 추적 가능.

**왜 중요한가**: 대형 터빈의 고장은 갑자기 발생하지 않는다. 수주\~수개월에 걸쳐 특정 주파수 성분이 서서히 커진다. Waterfall은 이 "성장 패턴"을 시각화하는 핵심 수단.

### 5.4 3D Orbit — 왜 XY 궤적인가

**문제**: X방향 진동, Y방향 진동을 각각 보면 크기는 알지만 "축이 어떤 방향으로 움직이는가"를 알 수 없다. 회전체 고장은 방향성을 가진다.

**선택**: X센서와 Y센서 신호를 동시에 플롯 → 축의 2D 궤적(Orbit)을 그린다. 원형=정상, 8자=오일 훨, 타원 쏠림=미스얼라인먼트.

**ISO 7919-3 기준을 채택한 이유**: 회전체 축 진동에 대한 국제 표준 → 원프레딕트가 임의로 정한 것이 아니라는 점이 고객 신뢰도 확보에 필수.

**"3D"인 이유**: 시간 축을 추가 → 궤도가 시간에 따라 변하는 것을 추적 가능. GS Caltex 엔지니어들이 "AI 결론이 아닌 원시 데이터를 직접 보겠다"는 니즈에 직접 대응.

### 5.5 베어링 전용 카드 화면 (Scene 13\~18) — 왜 별도 화면인가

**문제**: 가스터빈에서 베어링은 교체 주기가 있는 소모품이면서, 조기 이상이 가장 많이 발생하는 부위다. 메인 대시보드의 전체 현황만으로는 충분하지 않다.

**선택**: 베어링 번호별 전용 카드 화면(Scene 13\~18) → 각 베어링의 진동 크기, ISO 등급, 베어링 간극 비율을 집중 표시.

**베어링 간극 비율 기준의 출처**: 설비 제조사 스펙에서 유래. <30%=정상, 30\~50%=경고, >50%=알람.

### 5.6 15개 Fault Mode AI 분류 — 왜 하필 15개인가

확인 필요 — 정확한 선정 근거는 문서에서 확인되지 않음.

**배경**: 터보기계 진동 진단 표준에서 주요 고장 모드는 약 10\~20가지로 분류됨 (언밸런스, 미스얼라인먼트, 오일 훨, 베어링 결함, 축 균열, 루즈니스 등). AI 모델이 분류하는 15개 = 이 표준 고장 모드를 알고리즘 팀이 학습 가능한 단위로 정의한 것.

**기획적 의미**: 단순 임계치 알람이 아닌 "무슨 고장인지까지 알려준다"는 것이 경쟁 우위. 숫자 자체보다 이 컨셉이 핵심.

**구현 방식**: 채널 ID 30만번대 11\~24번이 15개 fault mode 리스크 스코어에 1:1 대응.

### 5.7 Dynamic Threshold (v2.6) — 왜 고정 임계치가 안 되는가

**문제**: 가스터빈 기동·정지 과정에서 진동이 일시적으로 크게 증가한다. 고정 임계치를 쓰면 기동 중 매번 알람 → 오탐 다발 → 운전원이 알람을 무시하게 됨.

**선택**: RPM에 따라 임계치가 동적으로 변하는 Dynamic Threshold. RPM이 낮을 때는 임계치를 높게 → 기동/정지 과정의 정상 진동 증가를 알람으로 처리하지 않음.

**왜 v2.6에서야 나왔는가**: 초기 버전은 정상 상태 운전 모니터링에 집중했다. GS Power, 중부발전 신보령 등 실제 운영 고객 피드백에서 "기동 시 알람 폭발" 이슈가 반복되며 필요성이 확인됨. 현재 개발 홀드 상태.

### 5.8 Scene JSON 시스템 — 왜 JSON 설정 파일인가

**문제**: 각 사이트마다 설비 구성이 다르다. 하드코딩된 UI를 만들면 사이트마다 개발 작업이 필요하다.

**선택**: 화면 구성을 JSON 설정 파일로 분리 → 개발자가 JSON만 작성하면 새 사이트 화면 생성 가능. "Config = Code" 패러다임.

**남은 한계**: 좌표가 픽셀 절대값 → 화면 크기 바뀌면 레이아웃 깨짐. JSON 작성이 개발자만 가능한 작업 → 납품마다 개발자 투입(3\~5일). 이 한계가 다음 세대(PDX) "Config = Data" 패러다임의 직접적 출발점.

## 8. 레슨런 (Lessons Learned)

경보가 울려도 "AI가 왜 그렇게 판단했는지 모른다"는 이유로 현장에서 무시된 사례가 반복됐다. **설명 가능성(Explainability)은 기능이 아니라 신뢰의 조건이다.** FFT 뷰, Fault 근거 표시가 필수인 이유.

Scene JSON 픽셀 좌표 방식은 신규 사이트마다 개발자가 3\~5일 투입을 요구했다. 영업이 고객을 늘려도 납품이 따라오지 못하는 구조. **제품 납품 비용이 증가할수록 시장 접근성은 낮아진다.**

OPC-DA 기반 수집기의 COM/DCOM 불안정으로 데이터 수집이 끊기는 이슈가 반복됐다. 아무리 정확한 진단 알고리즘을 갖춰도 데이터가 없으면 신뢰를 잃는다. 서비스 가용성을 고객보다 늦게 파악하는 것 자체가 신뢰 문제다.

특정 고객 요구가 제품 로드맵을 주도하게 되면 범용 제품으로서의 방향성이 흐려진다. 스케일 확장을 막는 가장 흔한 패턴.

대형 산업용 가스터빈을 운영하고 비용을 지불할 의사가 있는 국내 기업의 수는 제한적이다. 시장 규모 검증 없이 제품 고도화에 집중하면 TAM이 이미 좁다는 사실을 늦게 깨닫게 된다.

OPC-DA는 처음에는 어쩔 수 없이 채택했지만, 이후 가용성 문제의 원인이 되었다. 신규 구현에서는 처음부터 현대 프로토콜을 선택해야 한다.
