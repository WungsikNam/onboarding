## 2. 프론트엔드 기술 스택

**레포**: `cyclone-frontend-main`
**아키텍처 패턴**: Feature-based Architecture

```
src/
├── pages/     # 라우팅 최상위 컴포넌트
├── features/  # 비즈니스 로직 (api / model / ui)
├── widgets/   # 페이지 레벨 재사용 컴포넌트
├── entities/  # 비즈니스 엔티티 (데이터 모델, Zustand store)
├── shared/    # 전사 공통 코드 (API 클라이언트, UI 컴포넌트, 훅)
└── app/       # 앱 진입점 (라우팅, 프로바이더)
```

| **역할** | **기술** | **버전** |
| --- | --- | --- |
| UI 프레임워크 | React | 18.3.1 |
| 라우팅 | React Router | 7.9.1 |
| 데이터 페칭 & 캐싱 | TanStack React Query | 5.89.0 |
| UI 컴포넌트 라이브러리 | Ant Design | 5.27.4 |
| 언어 | TypeScript | 5.8.3 |
| 빌드 도구 | Vite | 7.1.6 |
| 전역 상태관리 | Zustand | 5.0.8 |
| 폼 관리 | React Hook Form | 7.62.0 |
| 그래프 시각화 (계보, 파이프라인) | Dagre + ReactFlow | |
| 차트 (모니터링) | ECharts | |
| 테스트 | Vitest | |

## 4. 데이터 파이프라인 — 메달리온 아키텍처

### 4.1 전체 흐름

```
[공장 설비 PLC / 센서]
      ↓  OPC UA / MQTT (실시간)
[Kafka 대기열]          ← 초당 수만 건을 안전하게 버퍼링
      ↓  1분 단위 압축 적재
BRONZE — MinIO/S3 Raw 버킷
            원천 데이터 그대로 보존 (JSON/Parquet)
            Cyclone: Bucket 자산, Tier 4, Bronze 마크
      ↓  Spark 정제 (노이즈 제거, 결측치 보간)
SILVER — Apache Iceberg 표준 테이블
            정형화·표준화된 신뢰 데이터
            Cyclone: Table 자산, Tier 3, Silver 마크
                      + 도메인·태그·용어사전 매핑 완료
      ↓  5분 집계 + ERP/MES/HR 조인 + AI 추론
GOLD  — 비즈니스 분석용 최종 테이블
            의사결정 및 BI 직결 고부가가치 자산
            Cyclone: Tier 1~2, Gold 마크, Lineage 완성
```

### 4.2 레이어별 핵심 처리

| **레이어** | **핵심 처리** | **접근 권한** |
| --- | --- | --- |
| **Bronze** | PLC/센서 신호 → Kafka → MinIO 1분 단위 적재. 가공 없음, 무결성 최우선 | 데이터 엔지니어·인프라 관리자만 |
| **Silver** | 노이즈 스파이크 필터링 (**직전 3개 평균 대체**). 결측치 보간 (Forward-Fill/선형). Iceberg 포맷 변환 + 시간 파티셔닝 | 해당 공정 엔지니어·설비보전원 |
| **Gold** | 5분 단위 집계 (평균·최대·표준편차). 이기종 Join (센서+ERP+HR). AI 점수 부가 (`anomaly_score` 컬럼) | 공장장·현장 반장. 모바일 알림 연동 |

### 4.3 데이터 동기화 주기

| **데이터** | **주기** | **이유** |
| --- | --- | --- |
| 설비 센서 Raw | 실시간 스트리밍 (수 초) | 유실 방지 |
| 이상감지 알림 | 즉시 (수 초 이내) | 골든타임 대응 |
| 설비 정보·CAD 도면 | 일 1회 (새벽 2시 배치) | 도면은 거의 변경 없음 |
| 직원·교대조 정보 | 주 1회 (일요일 야간 배치) | 주간 편성 주기 |

## 5. 보안 및 권한 체계 (RBAC + ABAC)

### 5.1 두 가지 접근 제어 방식

| **방식** | **기준** | **역할** |
| --- | --- | --- |
| **RBAC** (역할 기반) | 사용자 역할 | "이 사람이 어떤 역할인가"에 따라 기능 접근 제어 |
| **ABAC** (속성 기반) | 자산에 붙은 태그 | 역할이 아무리 높아도 `[극비]`·`[PII]` 태그 자산은 차단 |

### 5.2 표준 Role 4종 (삭제·이름 변경 불가)

| **Role** | **주요 권한** | **Admin Console** |
| --- | --- | --- |
| **System Admin** | 모든 설정, DataSource 등록/삭제, 감사 로그, Role 정의 관리 | ✅ |
| **Domain Admin** | 자기 도메인 관리 (Phase 2에서 도메인 범위 분리 예정) | ✅ |
| **Member** | 자산 검색·조회, 메타데이터 편집, 권한 신청 | ❌ |
| **Viewer** | 검색·조회만 (읽기 전용) | ❌ |

Custom Role 생성 가능. 예: `Plant_1_Safety_Inspector` (1공장 PT 공정 한정 조회)

### 5.3 Permission 포함 계층

```
MANAGE  ⊃  MODIFY  ⊃  SELECT  ⊃  BROWSE
```

MODIFY를 부여하면 SELECT·BROWSE도 자동 허용. DB에는 최상위 Permission 1건만 저장.

### 5.4 접근 제어 핵심 원칙

| **원칙** | **동작** |
| --- | --- |
| **기본 차단 (Implicit Deny)** | 명시적 허용 없으면 모두 차단 |
| **최소 권한 (Least Privilege)** | BROWSE 권한 없는 자산은 카탈로그에 아예 노출 안 됨 |
| **명시적 거부 없음** | Allow만 존재. Allow 없으면 Deny. Explicit Deny 규칙 미사용 |

### 5.5 ABAC 태그 정책

| **태그** | **자동 적용 정책** |
| --- | --- |
| `[PII]` | 민감 컬럼 자동 마스킹. HR Admin만 원본 조회 |
| `[대외비/극비]` | 검색 결과에서 자산 자체가 숨겨짐. 명시적 허용 없으면 접근 불가 |

### 5.6 Time-bound 임시 역할

```
Role 할당 + 만료일 설정
  → 만료일 도래 → 자동 비활성 (SEC-401-EXPIRED)
  → 재사용하려면 새 할당으로 처리
```

### 5.7 접근 제어 흐름

```
사용자 접근 시도
    ↓
[1] RBAC 확인 → 역할 없으면 RBAC-001/002/003
    ↓
[2] Time-bound 확인 → 만료되었으면 SEC-401-EXPIRED
    ↓
[3] ABAC 확인 → 극비 태그면 SEC-403-NOGRANT
              → PII 태그면 민감 컬럼 마스킹 후 허용
    ↓
접근 허용 + 감사 로그 자동 기록
```

### 5.8 에러 코드

| **코드** | **상황** |
| --- | --- |
| `RBAC-001` | 잘못된 Role 이름 (영문·숫자·언더스코어만, 최대 30자) |
| `RBAC-002` | 중복 Role 이름 |
| `RBAC-003` | 활성 사용자 있는 Role 삭제 시도 |
| `SEC-401-EXPIRED` | 만료된 역할로 접근 |
| `SEC-403-NOGRANT` | 권한 없는 접근 |

### 5.9 감사 로그 기록 항목

* 로그인/로그아웃
* 데이터 자산 조회
* 메타데이터 수정 (수정 전/후 값)
* 태그 추가/삭제
* 권한 부여/해제
* 데이터 다운로드

> **현황**: 백엔드 기록은 되지만 **감사 로그 조회 UI 미구현**. 관리자가 조회할 화면 없음.

## 6. Data Trust Index 세부 산정 기준

```
Data Trust Index = (DQ Score × 0.6) + (메타데이터 충실도 × 0.2) + (활용도·안정성 × 0.2)
```

### 6.1 DQ Score (60%)

**검증 도구**: Great Expectations (자동)

| **검증 항목** | **측정 기준** |
| --- | --- |
| 완전성 (Completeness) | 결측치율 |
| 정확성 (Accuracy) | 값 범위 유효성 |
| 일관성 (Consistency) | 고유 키 충돌 여부 |
| 신선도 (Freshness) | 최근 업데이트 시각 |

### 6.2 메타데이터 충실도 (20%) — 기획자 직접 작업 영역

| **항목** | **점수** |
| --- | --- |
| 설명 (Description) 입력 | +20 |
| 소유자 (Owner) 지정 | +20 |
| 도메인 매핑 | +20 |
| 태그 1개 이상 부착 | +20 |
| 용어사전 80% 이상 컬럼 연결 | +20 |

> **기획자 역할**: 이 20%를 채우는 것이 기획자/데이터 오너의 핵심 거버넌스 업무.

### 6.3 활용도·안정성 (20%)

| **측정 항목** | **설명** |
| --- | --- |
| 정시 수집률 | 배치 스케줄 준수 비율 |
| 최근 30일 쿼리 빈도 | 실제 사용 빈도 |
| 90일 내 장애 이력 | 수집 실패 기록 |

### 6.4 인증 등급 기준

| **Trust Index** | **등급** | **Tier** | **의미** |
| --- | --- | --- | --- |
| 90 이상 | Gold | 1~2 | 신뢰할 수 있는 데이터. 의사결정 직결 |
| 70~89 | Silver | 3 | 보통 수준. 정제·표준화 완료 |
| 70 미만 | Bronze | 4 | 관리 필요. 원천 원시 데이터 수준 |

**Gold 인증 유지 조건**: Trust Index 90점 이상. 미달 시 Gold → Silver 자동 강등.

## 12. 아키텍처 설계 원칙 & 오픈소스 리스크

### 12.1 3대 아키텍처 원칙

1. **MSA 구조**: 모든 컴포넌트는 독립적으로 구성·실행 가능해야 함
2. **Must vs Optional 분리**: 필수 컴포넌트만 기본 구축. Optional은 고객 환경에 따라 선택
3. **오픈소스 래핑 구조**: 오픈소스 기능 한계를 기획 시 항상 함께 확인해야 함

### 12.2 오픈소스 활용 리스크 (개발팀 명시 항목)

| **리스크** | **내용** |
| --- | --- |
| 인터페이스 불일치 | 오픈소스 간 (OpenMetadata·Airflow·MLflow) 인터페이스 불일치 → 연동 오류 가능 |
| 버그 대응 지연 | 오픈소스 버그는 외부 커뮤니티 의존 → 장애 시 즉시 해결 어려움 |
| 보안 패치 지체 | 커스터마이징 시 최신 릴리즈 반영 지연 → 보안 패치 지체 가능 |

> **기획자 주의**: 신규 기능이 오픈소스와 연관될 경우, 해당 오픈소스의 기능 한계와 버전 이슈를 개발팀과 반드시 사전 확인.

### 12.3 Phase 1 Hard-Coding 잔재 이슈

Phase 1에서 고객사 환경을 Hard-Coding으로 구축한 잔재(명화공업 등)가 Phase 2 Low/No-Code 전환과 충돌 가능. 기획 시 이 지점을 개발팀과 확인 필요.
